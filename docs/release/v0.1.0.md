## Validated v0.1 surface

- Deterministic, local-first verification for Node.js projects.
- Git change collection and deterministic change classification.
- Recognized `test`, `lint`, `typecheck`, and `build` verification intents.
- Five built-in deterministic rules:
  - workflow permission changes;
  - runtime dependency additions;
  - secret exposure with redacted evidence;
  - authentication changes without related tests; and
  - source changes without tests.
- JSON-only configuration with schema validation and deterministic merging.
- Terminal, JSON, and Markdown report rendering.
- CLI command APIs for checking, initialization, explanation, help, and version
  output, with distinct PASS, REVIEW, FAIL, usage-error, and internal-error
  paths. The existing top-level dispatcher currently exposes help/version and
  retains the pre-migration usage error for the not-yet-wired `check` path.
- A GitHub Action adapter that reuses the shared engine boundaries, publishes
  structured outputs and summaries, and retains least-privilege read-only
  workflow examples.

## Risk model

Risk scoring is deterministic and uses the normative v0.1 model:

- severity weights: `info=0`, `low=5`, `medium=15`, `high=30`,
  `critical=50`;
- `test`, `typecheck`, and `build` penalties: `passed/skipped=0`,
  `error=30`, `failed=50`;
- `lint` penalties: `passed/skipped=0`, `error=10`, `failed=15`;
- finding and verification scores are summed and capped at `100`;
- finding confidence does not affect `RiskScore`;
- default thresholds are `review=15` and `fail=50`; and
- DiffSentry internal errors remain outside the risk model and use CLI exit
  code `3`.

## Runtime and platform validation

- Supported runtime policy: Node `>=24 <25`.
- The earlier pre-migration hosted matrix is historical evidence only. A fresh
  DiffSentry matrix on `ubuntu-latest`, `windows-latest`, and `macos-latest`
  using Node 24 is pending after the migration source is pushed.
- The local release-candidate quality gate also passed install, lint,
  typecheck, test, build, architecture validation, examples, and artifact
  checks.

## Distribution validation

The seven public packages were built and packed as ESM-only TypeScript
packages:

- `@felyx-fu/diffsentry-contracts`
- `@felyx-fu/diffsentry-core`
- `@felyx-fu/diffsentry-runtime-node`
- `@felyx-fu/diffsentry-rules`
- `@felyx-fu/diffsentry-config`
- `@felyx-fu/diffsentry-report`
- `@felyx-fu/diffsentry`

Fresh v3 tarballs were inspected for package metadata, repository identity,
workspace dependency conversion, root exports, declarations, CLI bin output,
and file allowlists. A clean external npm consumer installed the packed
artifacts, imported representative package roots, resolved strict TypeScript
declarations, and ran the packed CLI `diffsentry --help` and `--version`
smoke tests. The required `diffsentry check` invocation retains the existing
top-level usage-error behavior and is not claimed as a completed executable
check flow.

The GitHub Action remains a private Action artifact and is not part of the
public npm package set.

## Known non-blocking limitations and boundaries

- `scripts/check-package-boundaries.ts` remains the existing explicit
  placeholder and reports that deep public-import validation is deferred. The
  architecture check, package artifact gate, and external consumer checks
  passed; no deep boundary-analysis claim is made.
- The local development host is Node `25.9.0`, outside the supported range.
  This is not release evidence; the supported Node 24 policy and hosted Node
  24 matrix are the release evidence.
- The GitHub Action bundle and adapters were validated locally and through
  tests. No live third-party repository Action execution is claimed here.
- npm preflight found all seven new names absent from the public registry, but
  this machine was not authenticated (`npm whoami` and `npm access list
  packages` returned `ENEEDAUTH`), so scope publishability is unverified.
- Publication remains a separate trust boundary. npm publication, Changesets
  publication, tag creation, GitHub Release creation, release workflow
  execution, and NPM_TOKEN use were not performed.

Actual release still requires separate explicit user authorization.
